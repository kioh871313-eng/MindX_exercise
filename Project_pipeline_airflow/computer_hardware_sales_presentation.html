Core design principle

SQL owns data cleaning, transformation and modelling. Python DAG code focuses on orchestration, parameter passing and execution logging.

This separation keeps business logic database-native, easier to review, test and maintain—while Airflow manages dependencies and run control.

Medallion Architecture

Three layers, three
clear responsibilities

01 · Bronze

Raw landing zone

Schema: bronze
Table: raw_hardware_sales

  • All incoming columns stored as TEXT
  • Snapshot batches appended on load
  • Tracks source file and ingestion time
  • Retains recent batches for 7 days
02 · Silver

Cleaned source of truth

Schema: silver
Table: clean_hardware_sales

  • Parses dates and casts data types
  • Normalizes text and numeric values
  • Filters invalid records and deduplicates
  • Recalculates business measures
03 · Gold

Analytics data mart

Schema: gold
Fact: fact_sales

  • Four conformed dimensions
  • Product and customer use SCD Type 2
  • Date and geography use Type 1
  • Surrogate keys support analysis

Bronze → Silver

Silver reads the latest Bronze snapshot per source file using the maximum _ingested_at value.

Silver → Gold

Dimension tables are built first. The fact table is then loaded by joining Silver records to the dimensions.

Scheduling & Change Detection

Run only when data
needs to be processed

SCHEDULED · HOURLY

Change detection

Airflow compares each S3 object's LastModified timestamp with pipeline_last_run_ts.

YES

New or updated file → load and run the full pipeline.

NO

No changes → ShortCircuitOperator skips downstream tasks.

MANUAL · TRIGGER DAG

Full reload

A manual trigger bypasses the CDC timestamp check and loads all S3 files as a fresh snapshot.

Useful after a SQL logic change: reload source data and reprocess it through Silver and Gold using the updated transformation rules.

Checkpoint design protects data completeness

1 · Capture STARTRecord the run start timestamp in XCom.
2 · Process dataIngest, clean, model and validate.
3 · Full success?Only successful upstream tasks allow checkpoint update.
4 · Save checkpointPersist the captured start time as the new UTC checkpoint.
The START time is saved—not the END time—so files uploaded while a run is in progress can still be detected on the next run. Failed runs do not advance the checkpoint.
Data Quality & Validation

Quality gates at every
processing layer

Validation is implemented as dedicated SQL-based tasks. Hard failures stop the pipeline and prevent the CDC checkpoint from advancing.

Bronze · Warn-first

Accept raw, check usability

  • Table must not be empty
  • Six required columns must exist
  • NULL order_id above 50% → fail
  • NULL rate up to 50% → warn
  • Duplicate rate above 30% → warn
  • No ingestion in last 2 hours → warn
Silver · 13 strict checks

Enforce clean records

  • Required IDs are not NULL
  • No duplicate order_id
  • Quantity, price and cost ≥ 0
  • Discount between 0 and 1
  • Profit reconciles to revenue − cost
  • Valid order/ship date sequence
  • At least 60% of valid Bronze rows
Gold · 15 strict checks

Protect analytical integrity

  • Dimensions and fact are populated
  • One current row per product/customer
  • SCD2 date ranges are valid
  • Fact order_id is not NULL
  • Dimension/date keys resolve
  • Profit reconciliation passes
  • Fact row count ≥ Silver row count

Examples of source issues handled in transformation

Duplicates & NULL IDs
Deduplicate records and filter unusable identifiers.

Mixed date formats
Route date strings through format-aware parsing.

Text & numeric noise
Normalize casing, trim whitespace, remove commas.

Invalid measures
Filter negative values and recalculate sales measures.

EMAIL ALERTS · SMTP

Two notification paths

[WARNING]Soft validation issues only. Pipeline continues.
[FAILURE]Hard validation check failed. Task raises and pipeline stops.
[ERROR] Task exceptionUnexpected task errors trigger Airflow's on_failure_callback with task name, run ID and exception message.

Each validation task sends one consolidated message after its checks. No email is sent when all checks pass.

Alert setup: recipient is configured with ALERT_EMAIL in the environment file; SMTP host and credentials are stored in the Airflow smtp_default connection. Leaving the recipient blank disables email alerts.

Airflow Variables

s3_bucket_nameTarget S3 bucket
s3_prefixSource folder path

Variables store non-sensitive pipeline configuration. The initial checkpoint is set far in the past for the first full load.

AWS and DWH credentials are not stored in code, SQL or Compose configuration.

Encrypted storage

Airflow metadata DB stores connection credentials encrypted.
